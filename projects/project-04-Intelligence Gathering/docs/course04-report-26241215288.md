## 4. 修改及前后对照

### 4.1 去重缺陷与修复

旧逻辑在 `_normalize` 将标题截成 500 字符、正文截成 4000 字符、URL 截成 1000 字符之后，将三字段拼接并计算 SHA-1。正文前 4000 字相同但尾部不同的两条记录具有相同指纹。旧入库又对截断字段计算一次指纹，单独修复分析层仍会发生数据库合并。

新增 `pipeline/content_identity.py`，对**截断前**的标题、正文、URL 分别合并连续空白、去除首尾空白，再序列化为固定字段顺序的 JSON 数组，使用 UTF-8 计算 SHA-256。字段数组避免拼接边界歧义。输出形如 `v2:sha256:<64位小写十六进制>`，存入分析记录的 `content_fingerprint`，由分析与入库共同使用。

展示及摘要长度限制保持原有行为。不同 URL 即使正文相同也保留；没有实施 URL 规范化、同义词匹配或模糊去重。修复效果来自完整字段和明确字段边界，不仅是更换哈希算法。

旧分析记录缺少新字段或其值为 null 时继续使用原入库 SHA-1 算法；其他新字段值须通过格式和版本校验，非法值明确报错，不静默回退。数据库已有 TEXT 指纹列无需迁移，也不自动修改历史数据。

### 4.2 接口变化

现有函数调用参数、HTTP 路径和已有返回字段不变。分析 JSONL 新增 `content_fingerprint`；分析元数据新增 `duplicate_count`、`empty_count` 和 `fingerprint_version`。数量在成功解析、读取上限以内满足：

```text
input_count = duplicate_count + empty_count + scope_excluded + output_count
```

该等式不包含被原有解析器跳过的 JSONL 坏行。本次原始输入没有坏行。旧数据库字段和旧分析记录均可继续使用；新旧版本指纹共存会使同一历史内容再次导入时可能出现两个文档，需以后另行设计迁移。

### 4.3 实测结果

“旧版”对照在同一份新采集 JSONL 上复现原指纹和原主题筛选逻辑，并非重新采集后比较不同样本。

| 场景 / 指标 | 旧逻辑 | 修复后 |
| --- | ---: | ---: |
| 公开资料输入 | 10 | 10 |
| 空内容 / 重复 | 0 / 0 | 0 / 0 |
| 主题排除 | 8 | 8 |
| 输出记录 | 2 | 2 |
| 合成边界样本：2 条长文的唯一记录数 | 1（误合并） | 2 |

公开样本没有出现此类碰撞，因此不能宣称真实数据去重率得到提升。合成样本使用相同标题、相同 URL、超过 4000 字的相同前缀及不同尾部，在测试中直接验证了旧碰撞和新指纹不同；集成测试进一步确认两条不同长文同时入库并生成不同归档。

真实实验产生 2 个数据库文档、2 个证据摘录、2 份学术 Markdown。重复导入同一分析文件后文档数仍为 2。脚本等待 1.1 秒后再导入，以避开现有按秒生成运行 ID 的限制，不伪造运行时间。
